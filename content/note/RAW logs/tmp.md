## TODO：字段层面要做语义相似度

现在的 plan 校验对大量自然语言字段走"字符串全匹配"，会因为同义改写或格式差异被误判为不可用。优先做规则归一化，归一化失败再用 embedding 相似度兜底。按字段分：

已经做了：

- 候选车系、车系版型（embedding + 覆盖匹配 + 尾缀兜底）
- 能源类型（`desc_similarity_threshold`）
- 车辆功能配置（`desc_similarity_threshold`）

还没做但应该做：

- 二手车需求，车辆用途（"通勤" vs "上下班通勤"）
- 车辆特点（"有排面和豪华"）、配置倾向性（"动力强加速迅猛" vs "加速快"，"价格低" vs "性价比高"）
- 新能源配置：电池类型、电芯品牌、快充/慢充、800V 等自由文本
- 电机配置：电机类型、电机数、电机布局
- 车辆用途：家用 / 通勤 / 自驾 / 接送小孩
- 用车人群：新手 / 年龄标签 / 家庭结构
- 内部配置、外部配置（配置项口径多、易同义改写）
- 其他需求、改装信息（自由文本）
- 车辆颜色：银灰 / 银色 / 珍珠白等近义
- 车辆类型、车身级别、驱动方式、变速箱配置、悬架配置、车门、座位布局（优先枚举映射，失败再相似度）

几个特殊规则：

- "必要"和"强烈"可混用。
- 多出来的 field 如果是"数量限制"，先不判错。
- 座位布局要让"总数一样就不算冗余条件"，比如 `座位布局##2+2+2##必要` 和 `座位布局##6座##必要` 算等价。
- 不同 field 但值相同也不算冗余，比如 `内部配置##方向盘加热` 和 `车辆功能配置##方向盘加热` 算等价。

## 当前 plan 校验规则 SOP

按当前代码逻辑，plan 输出和 label 做以下对比，产出"可用 / 不可用"判定以及错误标签。

### select

- output 包含 label 即可视为可用；
- output 比 label 少：如果 output 的 select 数量 ≥ 5，默认可用；否则按 label 做缺失检查并报错。

### where

除"候选车系 / 车系版型"之外的 where 条件，按原逻辑做字段 / 值 / 倾向性 / 排除的全匹配判定可用性；where 缺筛选条件仍算可用。

"候选车系 + 车系版型"走 embedding 余弦相似度：抽取后拼成文本对比，相似度 ≥ `similarity_threshold` 视为相同，否则该 params block 判为不可用。

多候选车系（≥ 2）场景：每个"候选车系 + 紧随的车系版型"构成一组，和 label 侧的组做一一覆盖匹配；只要有一组不过阈值就不可用。实现里会寻找一组能让所有 pair 都过阈值的匹配方式，避免仅因顺序差异误判。

为了鲁棒性，相似度取四种对比的 max：

- output(车系+版型) vs label(车系+版型)
- output(车系) vs label(车系)
- output(车系+版型) vs label(车系)
- output(车系) vs label(车系+版型)

另外车系文本候选里会加一份"去掉尾部英文字母后缀"的版本（如 `515CDI` → `515`），避免尾缀把相似度拉低导致误判。这套 max-相似度逻辑也用于 params block 的兜底对齐。

Params block 对齐：原本 `_block_key()` 只靠字符串相等对齐，现在找不到精确 key 时会用"候选车系 + 车系版型"的相似度做兜底，把 label block 对齐到最相近且过阈值的 output block。

新增的 `desc_similarity_threshold`（默认 0.7）用来控制描述文本的相似度阈值，适用于车辆功能配置、能源类型。

"版型替代字段绑定"：只有 1 组候选车系的场景下，如果某侧缺少车系版型，但 where 里有座位布局，会把它绑定为该组的版型并从剩余 where 中消费掉。

### orderby（order）

按全匹配做缺失 / 多余校验（字段 / 值 / 倾向性 / 排除，顺序无关）。当前只产出错误标签，不参与"可用 / 不可用"判定。

### groupby（group_by）

- 缺失：label 有但 output 没有；
- 多余：output 有但 label 没有；
- output 的 group_by 里出现"候选车系"直接报错。

同样只产出错误标签，不参与"可用 / 不可用"判定。
