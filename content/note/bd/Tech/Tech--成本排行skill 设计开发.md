做一个「成本排行」Skill 的过程笔记。需求本身很简单：用户给出部门名、维度、产品，Skill 返回该部门的成本排行。能力依赖另一个团队提供的 API，这个 API 有两个前置条件——用户的 JWT 鉴权、以及用户在该平台完成授权。我先拿自己的 JWT 把链路跑通，再从一版能用的脚本迭代到现在的设计。

下面是这次开发过程中真正踩过的几个坑，以及由此沉淀出来的六条原则。用我自己的话说，这些原则的共性只有一句：**Skill 是给模型用的工具，不是给人读的代码。**

![[Tech--成本排行skill 设计开发-1.png]]

## 一、鉴权信息不该由 Skill 承担

![[Tech--成本排行skill 设计开发-2.png]]

第一版图省事，把服务账号换 JWT 的逻辑直接塞在脚本里，凭证硬编码在源码中。能跑，但很快就暴露了三个问题：Skill 开始感知底层鉴权细节、凭证暴露在源码里、换个用户这套逻辑就完全失效。

平台侧其实提供了中间件机制，可以把 JWT 注入到上下文里，Skill 从上下文读即可。于是鉴权对 Skill 彻底透明——要是没有这类基础设施，退一步放环境变量也行，反正不该在 Skill 里自己干。

结论是 Skill 要做无状态的执行者，鉴权、配置这类外部依赖一律从上下文或环境变量注入。

## 二、脚本不要崩，要会解释

![[Tech--成本排行skill 设计开发-3.png]]

反复调试下来我认为这是最关键的一条：**脚本可以返回错误信息，但绝对不能把 Python traceback 直接抛给模型**。

调用方是模型，不是人。模型拿到 `KeyError` 或 `ConnectionTimeout` 的 traceback，大概率就是懵——它不知道这是参数问题、上游问题还是网络问题，只会反复重试或直接放弃。正确的做法是优雅失败：所有可能出错的位置 try-except 兜住，失败时返回结构化的错误描述，告诉模型究竟哪一层出了问题、可以怎么重试。

```python
def query_cost(department, dimension):
    try:
        data = api.get(department, dimension)
        if "result" not in data:
            return {
                "success": False,
                "error": f"API 返回格式异常，缺少 result 字段，原始响应: {data}",
            }
        return {"success": True, "data": data["result"]}
    except ConnectionError as e:
        return {"success": False, "error": f"API 连接失败: {e}，请稍后重试"}
    except Exception as e:
        return {"success": False, "error": f"未知错误: {e}"}
```

这里的"错误信息人类可读"其实是幌子，真正的目标是模型可读。脚本鲁棒性是 Skill 可用性的前提——模型拿到的应该是一份诊断报告，而不是崩溃现场。

## 三、以 Case 养 Skill

![[Tech--成本排行skill 设计开发-4.png]]

代码写得再健壮，不过测试都是纸上谈兵。我最后的做法是让模型先生成十几条 case，再让模型自己去跑，根据结果反过来调整脚本和说明文档。

这个过程里我意识到一件事：Skill 天然是测试驱动的。先准备 case，让真正会部署的那个 Agent 去跑，观察它在哪些 case 上表现不好——是参数传错、说明文档不清晰，还是脚本返回的信息不够。然后针对性地改，再跑一轮。比自己拍脑袋想 Skill 该长什么样高效得多，因为**模型的实际使用行为才是最真实的反馈**。

推荐平台：[AI PaaS Skill](https://cloud.bytedance.net/ai/skill?x-resource-account=public&x-bc-region-id=bytedance)，可以直接调试。

## 四、参数不全，让模型去问人

![[Tech--成本排行skill 设计开发-5.png]]

还有一个容易忽视的场景：用户说"查一下成本"，没指定部门也没指定维度。模型该不该猜？我的结论是不该。

正确的行为是主动向用户追问。这意味着 Agent 侧——尤其是问答助手这种场景——需要一个"向用户提问"的工具。参数不完整时，模型应该礼貌地追问，而不是胡乱填值去碰运气。

好的 Skill 设计不只要回答"能做什么"，还要回答"不确定时怎么办"。

## 六条原则

这几个坑走完之后沉淀下来六条原则，按依赖关系列：

### 1. 测试驱动，以 Case 养 Skill

不要追求一次性写对。先准备覆盖正常/异常/边界的 case 集合，让真正要部署的 Agent 去跑，从日志里找问题，针对性迭代。每一轮都会让 Skill 更稳。

### 2. 精确暴露，渐进披露

暴露给模型的信息越精确、越结构化，它用得越准。类似最小权限原则：只暴露必要的参数和返回值、复杂内部逻辑对模型隐藏、分层组织（核心用法放 SKILL.md 顶部，细节参考放 references）、非必要不直接暴露实现代码。

### 3. 主动发问，拒绝猜测

参数不全就追问用户。在 Agent 层面接一个"向用户提问"的工具，对问答助手类场景尤其重要，能显著降低错误调用率。

### 4. CLI 化封装，降低耦合

可选但推荐：把脚本做成 CLI，发布到线上，SKILL.md 里写清楚安装方式，Agent 走 Bash 调用。好处是 Skill 与 Agent 通过标准 I/O 解耦、CLI 可以独立测试和版本化、多个 Agent 可以复用同一个 CLI。

### 5. 优雅失败，反馈真因

脚本可以失败，但要让模型能接得住失败。直接抛 traceback 的话模型只能重试或放弃；返回空结果没有说明，模型不知道问题在哪；返回结构化错误信息，模型才可能理解错因、调整参数、有效重试。

把模型当需要明确指令的新人，不要当能看懂堆栈的老程序员。

### 6. 透明度控制，适度抽象

只对模型暴露接口定义和关键逻辑的伪代码，核心实现封装在 CLI 或服务内部。有些 Agent 有能力读源码，但这不等于就要把实现全摊开。接口稳定，实现变化模型无需感知——这是原则 2 的延伸：不只是控制信息量，更要控制信息层级。模型需要知道"做什么"和"怎么调用"，不需要知道"怎么实现"。
