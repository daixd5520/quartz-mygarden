# 设计原则

单一职责、描述清晰、渐进披露

## 一、需求背景：一个「成本排行」Skill

我要做的 Skill 功能并不复杂——**用户输入部门名称****、****维度****、产品****，Skill 查询并返回该部门的成本排行**，告诉用户哪块成本消耗最大。

这个能力依赖另一个团队提供的 API。该 API 有两个前置条件：

1. 需要用户的 **JWT** 进行身份验证
2. 用户需要在该平台完成**授权**

因为当时还在测试阶段，我先给自己申请了 JWT，完成了鉴权，开始了第一版开发。

# 二、坑

### 2.1 第一个坑：鉴权信息不该写在 Skill 里

![[Tech--成本排行skill 设计开发-2.png]]

一开始图省事，我直接把服务账号获取 JWT 的机制写在了脚本里——硬编码了服务账号的凭证信息。

跑起来倒是能用，但很快意识到这是一个**严重的设计问题**：

- Skill 不应该感知底层的鉴权细节
- 服务账号的凭证信息直接暴露在脚本中，既不安全，也不可维护
- 如果换一个用户使用这个 Skill，鉴权逻辑就完全不适用了

后来我发现平台提供了**中间件机制**，可以将 JWT 注入到上下文中，Skill 只需从上下文里读取即可。这样一来，鉴权对 Skill 来说就变成了**完全透明**的——Skill 专注做自己的事，鉴权交给基础设施。

或者也可以写到环境变量里。

**教训**：Skill 应该是"无状态"的执行者，外部依赖（鉴权、配置等）应通过上下文/环境变量注入，而非硬编码在 Skill 内部。

### 2.2 第二个坑：脚本绝对不能报错

![[Tech--成本排行skill 设计开发-3.png]]

在反复调试中，我总结出一条**铁律**：

> **脚本可以返回错误信息，但绝对不能直接抛异常崩溃。**

为什么？因为 Skill 的调用者是模型。模型拿到一个 Python traceback，大概率会"懵圈"——它不知道该怎么修复一个 `KeyError` 或者 `ConnectionTimeout`，只会反复重试或者干脆放弃。

正确的做法是：**优雅地失败**。

- 所有可能出错的地方都加上 try-except
- 错误时返回结构化的错误信息，清楚地告诉模型"哪个参数不对"或"哪个服务不可用"
- 模型拿到这些信息后，可以自主调整参数重试

```Python
# 不好的写法
def query_cost(department, dimension):
    data = api.get(department, dimension)  # 可能抛异常
    return data["result"]                   # 可能 KeyError

# 好的写法
def query_cost(department, dimension):
    try:
        data = api.get(department, dimension)
        if "result" not in data:
            return {"success": False, "error": f"API 返回格式异常，缺少 result 字段，原始响应: {data}"}
        return {"success": True, "data": data["result"]}
    except ConnectionError as e:
        return {"success": False, "error": f"API 连接失败: {str(e)}，请检查网络或稍后重试"}
    except Exception as e:
        return {"success": False, "error": f"未知错误: {str(e)}，请联系管理员"}
```

我们对代码做了大幅调整，给所有常见错误都增加了**人类可读的错误信息返回**——其实是"模型可读"的。

**教训**：脚本的鲁棒性是 Skill 可用性的基石。模型不是程序员，它需要的是"诊断报告"，而不是"崩溃现场"。

### 2.3 转折点：测试驱动的觉醒

![[Tech--成本排行skill 设计开发-4.png]]

代码写得再健壮，不经过充分测试也是纸上谈兵。

我当时的做法是：让大模型生成十几条测试 case，然后让模型自己去执行这些 case，再根据返回信息去调整脚本或说明文档。

这个过程让我有了一个重要的认知：

> **Skill 一定是测试驱动的。先写测试 case，再让模型使用 Skill，根据结果不断迭代，而不是一开始就把 Skill 写"死"再反复修改。**

后来我看了一些关于 Skill 编写的文档，其中也印证了这个观点。核心思路是：

1. 先准备一批覆盖常见场景的测试 case
2. 让模型（最好是你真正要部署的 Agent）执行这些 case
3. 观察模型在哪些 case 上表现不好——是参数传错了？是说明文档不清晰？还是脚本返回信息不够？
4. 针对性地调整 Skill，然后重复上述过程

这种方式比"自己拍脑袋想 Skill 该长什么样"要高效得多。**模型的实际使用行为才是最真实的反馈。**

### 2.4 新的思考：人工介入机制
![[Tech--成本排行skill 设计开发-5.png]]
还发现一个问题：**模型有时候不知道该怎么用这个 Skill**。比如用户说"查一下成本"，但没有指定部门和维度——模型应该去猜吗？

答案是不应该。模型应该**主动向用户发问**。

这意味着在 Agent 的设计中，尤其是问答助手类场景，最好增加一个**"向用户提问"**的工具。当 Skill 需要的参数不完整时，模型应该礼貌地追问，而不是胡乱填充参数去碰运气。

**教训**：好的 Skill 设计不仅要考虑"能做什么"，还要考虑"不确定时怎么办"。人工介入机制是可靠性的重要保障。
### 原则一：测试驱动，以 Case 养 Skill

不要试图一次性写出完美的 Skill。**先构建测试用例集，让模型在实际调用中暴露问题，再持续迭代改进。**

|   |   |   |
|---|---|---|
|阶段|做什么|关键产出|
|准备期|设计覆盖正常/异常/边界场景的测试 case|测试用例集|
|执行期|让目标 Agent 执行所有 case|执行日志与结果|
|分析期|对比预期与实际，定位失败原因|问题清单|
|迭代期|针对性调整脚本/说明文档/参数设计|新版本 Skill|

这是一个循环过程，每一轮迭代都会让 Skill 变得更强。

### 原则二：精确暴露，渐进披露

**不是所有信息都需要暴露给模型。** 暴露的信息越精确、越结构化，模型的理解和使用就越准确。

这与软件工程中的"最小权限原则"类似：

- 只暴露模型需要的参数和返回值
    
- 复杂的内部逻辑对模型隐藏
    
- 分层组织信息：核心用法放在 SKILL.md 顶部，详细参考放在 references 目录
    
- 非必要时不直接暴露核心实现代码，可以只提供伪代码或关键逻辑
    

### 原则三：主动发问，拒绝猜测

当模型不确定如何使用 Skill 时，一定要**主动向用户发问**，而不是盲目猜测参数。

在 Agent 中增加"向用户提问"的机制，可以显著降低错误调用率，提升用户体验。这一点在问答助手类场景中尤为重要。

### 原则四：CLI 化封装，降低耦合

一个可选但推荐的做法是：将脚本做成 **CLI（命令行工具）** 的形式，打包发布到线上。在 Skill 的 SKILL.md 里写好安装方式，Agent 只需要调用 Bash 命令即可。

这样做的好处：

- Skill 与 Agent 之间通过标准 I/O 交互，解耦彻底
    
- CLI 工具可以独立测试、独立版本管理
    
- 不同 Agent 可以复用同一个 CLI 工具
    

### 原则五：优雅失败，反馈真因

**脚本可以失败，但必须优雅地失败。** 把错误的真实原因以结构化的方式反馈给模型，让它有能力自主诊断和调整。

|   |   |
|---|---|
|失败方式|模型能做什么|
|直接抛异常 (traceback)|什么都做不了，只能重试或放弃|
|返回空结果，无说明|不知道哪里错了，可能反复重试|
|返回结构化错误信息|理解错因，调整参数，有效重试|

核心原则是：**把模型当成一个需要明确指令的新人，而不是一个能看懂报错堆栈的老程序员。**

### 原则六：透明度控制，适度抽象

仅向模型暴露关键逻辑或伪代码，非必要不直接让模型读取源码。虽然有些 Agent 有能力读取 Skill 源码，但这并不意味着需要把所有实现细节都摊开。

- 只暴露接口定义和关键业务逻辑的伪代码
    
- 核心实现封装在 CLI 或服务内部，模型无需直接调用
    
- 保持适度的抽象层，减少模型对实现细节的依赖
    
- 当 Skill 逻辑变更时，只要接口不变，模型无需感知
    

这与原则二「渐进式披露」相呼应 —— 不仅是信息量的控制，更是信息层级的控制。模型需要知道 "做什么" 和 "怎么调用"，但不需要知道 "怎么实现"。
