# AI 选车问答系统问题拆解与演进方案

这是一套面向汽车导购场景的端到端问答系统，主线由 `Plan 模型`、RAG（网页检索 + 车型库检索）、`总结模型`、自动化评估四部分组成，覆盖从用户 query 到图文回复的完整链路。下面按"系统现状 → 核心问题 → 技术方案 → 训练与评测 → 多模态演进 → 车型库检索 → 落地排期 → 面试拷打题"的顺序展开，重点放在具体数字、失败复盘和可复用的工程选择上。

## 1. 系统现状

基座模型使用 `qwen3-4B/8B/30B-A3B` 与 `qwen3-0.6B` / `qwen3-1.7B` 搭配，judge 侧以 `deepseek-r1` 和 `doubao1.6-seed-thinking` 为主，数据生产同时调用 `doubao1.6-think` 与 `deepseek-r1` 互为校验。主要模块与当前选型：

- `Plan 模型` / `Plan-2 模型`：同一模型在不同阶段的叫法，主力 `qwen3-30B-A3B`，负责 query 理解、任务拆解、车型库工具调用规划。
- `总结模型`：最终 answer 生成，与多轮改写模型串联。
- 车型库检索：多路召回 + 粗排 + 精排的独立子系统，精排走 `qwen3-1.7B` 蒸馏的单塔相关性模型，端到端 P90 约 91ms。
- 自动化评估：`deepseek-r1` 和 `doubao1.6-seed-thinking` 作 judge，不直接做生成。
- 权威数据源：内部结构化库 + 厂商库，优先级高于开放网页。

## 2. 四类核心问题

现存问题收敛到四件事：显式意图分流放大误差、RAG 数据质量与冗余、训练信号稀疏、多模态缺口。表面分散，实际都指向一点——系统中心没有真正落在 query 理解与任务规划上。

### 2.1 显式意图分流系统性放大误差

传统多标签意图分类在选车这种语义连续的场景里很难刻稳。一条 query 经常同时带车型约束、属性偏好、对比需求和图片理解诉求，把这种高不确定性判断放到链路最前端，再让后面的理解、召回、表达都依赖它，前面偏一点，后面就是整条路径一起偏。

同时，每条下游链路都在服务预定义意图集合，系统实际优化的不是"理解这条 query"，而是"把这类 query 说得像样一点"，模板化表达因此越来越重。

### 2.2 RAG 的核心矛盾

线上经常停留在"用户问了就搜、能搜多少搜多少"。问题分三层：

1. 前置规划缺失：该不该检索、检索什么、要不要加时效性与事实性约束，没有决策点。
2. 基础检索模块不稳：网页检索与车型库检索缺独立评测集和持续迭代指标。
3. 后置融合粗放：多路结果回来以后，重复、互补弱、甚至彼此冲突的信息一起塞给 `总结模型`，让它在脏上下文里被动兜底。

### 2.3 训练信号稀疏

只盯着 `总结模型` 本身，很容易把问题归结成"模型还不够强"。真正矛盾是训练环境里的噪声和反馈确定性：RAG 召回带进来的脏输入 + 合成数据链路与自动化评估本身的不稳定，最终让模型在一个低反馈确定性环境里学兜底策略，而不是学稳定能力。

一次直接上 GRPO 的尝试给出了清晰信号：当前模型几乎不产生能被判为正确的答案，reward 极其稀疏，训练跑不起来。这不是 RL 算法问题，而是前面的数据、prompt、格式、任务拆分没把模型送到一个能被奖励函数有效区分的区间。

### 2.4 多模态是明确缺口

图片输入类 query 如果还按纯文本处理，用户感受到的不是"能力稍弱"，是"系统没理解他在问什么"。问题不在缺图片输入这一件事，而在 Plan 阶段没有视觉理解、RAG 阶段没有视觉素材回召与使用、总结阶段没有图文联合表达——视觉能力没进主链路。

## 3. 技术方案

### 3.1 Plan 中心化，意图分流降级为局部决策器

所有 query 先进入 `Plan 模型`，由它决定 query 的目标、需要哪些信息、要不要检索、检索源是哪些、表达怎样组织。系统前置任务从"给 query 贴标签"换成"搞清楚这条 query 要解决什么问题"。

某些场景确实需要分流的话，把"是否引入某条专门链路"做成一个独立二分类问题。分流模型只对"要不要走这条链"负责，不对 query 本身理解负责，职责边界清楚很多。

最终 answer 由 `总结模型` 生成，多轮改写模型做风格化后处理。三层各司其职：Plan 负责结构化理解与决策，总结负责回答生成，改写负责可读性。

### 3.2 RAG 拆成三段：权威源 / 基础检索 / 结果融合

检索规划分前置与后置两段。

前置由 Plan 驱动，回答三个问题：要不要检索、检索哪些类型的数据、是否引入时效性或事实性约束。检索由此从静态触发变成理解驱动的动态规划。

后置发生在结果返回之后，看结果数量、重叠度、互补性，再决定是否调用 LLM 数据融合。如果结果已经足够清晰，默认再走一层大模型融合只会把延迟和成本拉高。

基础检索模块要单独建设。网页检索重点是召回质量、来源可信度、冗余控制；车型库检索重点是实体边界识别、结构化召回、排序、候选合并。两条链路都必须有独立测试集、明确评估指标和日常迭代流程，不能只靠"线上看起来还行"判断。

权威数据源优先级要拉高。内部结构化库和厂商库不与普通网页源平权竞争——前置规划阶段识别哪些问题必须优先走权威源，后置融合阶段避免把权威源与低可靠源无差别混合。

### 3.3 Text2XML 而不是 Text2SQL

早期尝试过 Text2SQL，多表关联和复杂嵌套过滤下 LLM 准确率只有约 76%，括号/引号类语法错误占了相当比例。换成 XML 以后：

- 结构对 LLM 更友好，`<select>`、`<where>`、`<order>`、`<group_by>` 把查询指标与过滤条件解耦，生成幻觉明显下降。
- 有专门的 XML Parser 做硬校验，格式错的样本直接在数据产出阶段被拒掉，不会流进训练集。
- 对选车场景常见的 `order by 销量 / 热度`、`group by 车系` 天然友好。

一条实测数据：500+ query 自评下，XML 输出未发现格式错误；同期 SQL 输出的格式错误率远高于可接受阈值。

## 4. 训练与评测

### 4.1 数据生产：多模型协同 + Format Validator

数据产出流程走一种非严格意义上的 ReAct——用 `deepseek-r1` 和 `doubao1.6-think` 双路 Plan 生成，互为 Validator，`Format Validator` 单独再跑一道。

![[微信图片_20260412220812_13_9.png]]

两条硬结论。

**Format Validator 只做格式校验，不混其他任务。** 结构化输出场景里格式错是硬伤，不应该等到训练时再被动兜底。

**Format Validator 不能过度迷信小模型。** `doubao1.6-nothink` 这类更轻的模型在复杂 XML 格式检测上漏检率偏高，真正稳的是 `doubao1.6-think` 或 `deepseek-r1` 这类具备推理链的大模型。省这部分模型成本，最后多半把脏数据重新放回训练集，得不偿失。

### 4.2 拒绝采样 + 纠错式 SFT 先把下限抬起来

XML Parser 对训练数据做第一道拒绝采样，结构明显错误的样本直接拦在训练集之外。之后针对核心 badcase 做纠错式 SFT，高频问题集中在：

- `select` 粒度过细：倾向选出类别属性而不是具体指标。
- `select` 粒度过粗：选出聚合字段，无法回答具体问题。
- `select` 隐形决策指标缺失：query 暗含的关键决策维度没被带出来。
- `select` 核心指标缺失。
- `where` 过筛选：把软偏好当硬过滤。
- `where` 错筛选 / 条件幻觉。

3K 条人工标注纠错数据 + 专门的"粒度审计"类 prompt，配合 SFT，把意图边界识别准确率从不稳定状态拉到 **98.07%**（1403 条评测 case 上）。这个数字直接决定了下游 GRPO 有没有接手的可能。

### 4.3 GRPO 复盘：先 SFT 再 RL，不是反过来

GRPO 的第一次尝试失败，原因是典型的训练信号稀疏：初始模型在 `select` 粒度这类硬问题上几乎不产生可被判为正确的答案，reward 模型区分不出来，梯度噪声远大于信号。

复盘出来的判断很直接：**RL 适合做"80 到 95"，不适合做"0 到 60"**。把模型先用拒绝采样 + SFT 推到一个 reward 能稳定区分的区间（比如 `select` 准确率 90%+、格式准确率接近 100%），再让 GRPO 做增量，才是现实可行的顺序。

### 4.4 Dense 比 MoE 更适合结构化输出

输入不变的前提下，Dense 模型多次输出的连续性显著好于 MoE。结构化输出任务要求格式、字段边界、决策口径都尽量一致，MoE 在这类场景里更容易出现输出漂移。现阶段优先追求稳定性，Dense 作为主力；MoE 在创意性任务或允许风格浮动的场景再考虑。

### 4.5 自动化评估：judge 不承担生成

`deepseek-r1` 和 `doubao1.6-seed-thinking` 作评测模型，通过专门的 prompt engineering 给出可区分、可复用、可用于训练的反馈。judge 的任务是判分，不是替主模型答题——把两件事混起来，会让评估信号和生成目标互相污染。

## 5. 多模态能力要进主链路

短期不一步到位，但必须让视觉能力分别进入三处：

- Plan 阶段引入 VL-LLM：理解上传图片、识别关键信息、把视觉内容转成可规划的语义表示。
- RAG 阶段引入多模态输入：图片和视频作为可召回、可控使用的上下文，由 Plan 决定何时需要，并严格控制多模态上下文规模。
- 总结阶段引入具备多模态处理能力的模型：对强视觉诉求的 query，纯文本回复的体验上限太低，图文混合回答是必要能力。

长期要收敛成统一的多模态 Plan 和 VL 总结模型。前者负责输入级统一理解，后者负责输出级统一表达，系统不在不同模态之间反复做信息翻译，一致性才有保证。

## 6. 车型库检索（概览）

车型库检索是整套系统走向可控的关键底座——许多看起来属于 answer 或 plan 的问题，追根究底都落回这里。整条链路分四层：`Plan-2 / ToolPlan` 解析 query → 召回层（char 粒度倒排 / 向量 / 选车倒排，Quota Snake Merge 合并）→ 排序层（双塔粗排 + 单塔精排，LLM 蒸馏 + 5 档 Level-Wise Relevance）→ 应用层（结构化输出 + 综合得分 `0.6 / 0.3 / 0.1` + 澄清兜底）。

关键数字：车型边界识别准确率 **98.07%**（1403 case）、精排 P90 **91ms**、XML 格式 500+ query 零错。

这一层的完整设计、失败复盘、迭代节奏、长尾问题和面试拷打题拆在独立文档里：[AI 选车车型库检索设计](file:///Users/bytedance/Documents/quartz-mygarden/content/note/bd/work/AI%20%E9%80%89%E8%BD%A6%E8%BD%A6%E5%9E%8B%E5%BA%93%E6%A3%80%E7%B4%A2%E8%AE%BE%E8%AE%A1.md)。

## 7. 异构现在、收敛未来

当前搭配：多轮改写模型已完成一轮 SFT + GRPO；Plan 规划、Plan 回复思路、Plan-2 均以 `qwen3-30B-A3B` 为主力；总结层既有大模型主回答也有策略兜底；自动化评估靠 `deepseek-r1` 和 `doubao1.6-seed-thinking` judge。

这套异构组合的意义是在快速试错期内先把各环节做出来，比强行全链路统一模型更务实。长期看，理解层和生成层必须收敛，不能维持过多口径不同、风格不同的模型并行。

## 8. 落地优先级

分三层推进：

1. 车型库检索主链路打通：`Plan-2`、召回、排序、应用层形成可评测、可上线、可回溯的闭环。
2. 数据闭环立起来：多模型协同数据生产、`Format Validator`、拒绝采样、SFT 数据构造、自动化评估。
3. GRPO 与更强模型能力的增量优化放第三层。

按模块的排期锚点：

- `Plan-2 / ToolPlan`：先稳召回层与排序层的接口定义，再补训练与评测（2 月 2 日完成接口对齐）。
- 召回层：打通 char / embedding / 倒排三路，补齐在售 / 停售 / 即将上市等关键数据状态（2 月 9 日）。
- 排序层：双塔 + reranker 基线跑稳后再上领域化训练（2 月 13 日进入精排训练）。
- 应用层：召回结果接入 plan 与 answer，关键阶段日志打全便于排障。

## 9. 几条可以直接下注的判断

- 意图分流不该做成总开关，可以存在，但只能降级为局部决策器。
- RAG 的真正缺口是规划、融合、基础评测，不是多接几个数据源。
- GRPO 失败的第一问是"当前模型能不能稳定产出可被判正确的答案"。答案是否定的话，回去补 SFT、补数据、补 validator，而不是调 RL 超参。
- 多模态必须进主链路，Plan 和总结不进多模态，系统对图片场景永远只是反应迟钝的文本问答器。
- 车型库检索是整套系统走向可控的关键基础设施，值得单独重兵投入。
- 结构化输出场景优先 Dense，MoE 留给创意型任务。

## 10. 面试拷打模拟题

下面是基于项目复盘整理的十五道深度问题，覆盖架构、算法、工程、业务四个维度。Q1–Q10 是系统核心问题与复盘，Q11–Q15 深入多模态上线、权威源策略、GRPO 第二次设计、数据闭环、组织协同等更细的决策。

### Q1：为什么选 Text2XML 而不是 Text2SQL？

SQL 在多表关联和复杂嵌套过滤下 LLM 准确率只有 76% 左右，括号 / 引号类语法错误占比高。XML 三方面更稳：

- 结构对 LLM 更友好，`<select>`、`<where>`、`<order>` 把查询指标与过滤条件解耦，幻觉下降。
- XML Parser 硬校验可以做拒绝采样，格式错的直接拦在训练数据外。
- 对选车常见的 `order by 销量/热度`、`group by 车系` 天然友好。

500+ query 自评下 XML 输出未发现格式错误，作为这次选型的直接依据。

### Q2：GRPO 训练失败，能聊聊原因和复盘吗？

失败的直接原因是 reward 稀疏：初始模型在 `select` 粒度这类硬问题上几乎不产出可判为正确的样本，reward 模型区分不出来，梯度噪声远大于有效信号。

复盘结论：RL 适合做"80 到 95"，不适合做"0 到 60"。解法是先用 XML Parser 拒绝采样 + 3K 条纠错 SFT，把 `select` 识别准确率拉到 98.07%（1403 case），再让 GRPO 去做增量。这次之后的经验是先问"当前模型可被 reward 稳定区分吗"，区分不了就先回 SFT。

### Q3：多模态能力的短期和长期接入路径分别是什么？

短期不重做系统，但视觉能力要分别进三处：

- **Plan 阶段**：引入 VL-LLM 理解用户上传图片，把视觉信息转成可规划的语义表示，Plan 输出的结构化约束里带上图片里识别到的实体（车型 / 颜色 / 场景）。
- **RAG 阶段**：图片和视频作为可召回的上下文，由 Plan 决定何时调用，并严格控制多模态上下文规模。
- **总结阶段**：引入具备多模态处理能力的模型，支持图文混合输出。纯文本回复对强视觉诉求 query 的体验上限太低。

长期把 `Plan 模型` 进化成统一的多模态理解模型、`总结模型` 进化成统一的 VL 总结模型。输入级统一理解 + 输出级统一表达，避免系统在不同模态之间反复做信息翻译。

### Q4：权威数据源和网页检索怎么融合？

职责分工清楚：

- **权威数据源**（内部结构化库 + 厂商库）：负责事实正确性。价格、配置、参数、状态这类强事实 query 必须优先走这条路，优先级高于开放网页。
- **网页检索**：负责开放域补充——评测、对比、用户口碑、热点事件。

`Plan 模型` 在前置规划阶段决定走哪路，后置融合阶段避免把权威源和低可靠源无差别混合。权威和非权威混在一起会让 `总结模型` 在口径上迷失——用户问参数，系统把厂商库的官方数字和网络上的道听途说按相关性排序后并列呈现，等于没给用户权威答案。

### Q5：P90 91ms 这个指标包含 LLM 生成时间吗？怎么压测和优化的？

91ms 主要是精排模块（`qwen3-1.7B` 蒸馏的单塔相关性模型）的端到端耗时。优化手段：

- **蒸馏 + 推理加速**：LLM 教师蒸馏到 1.7B 学生，用 vLLM 框架做推理加速。
- **KV Cache 与输入长度控制**：输入 token 控制在 1500 以内，Attention 计算量可控。
- **Pipeline 并行化**：Plan 30B 虽然耗时长，但它一旦产出指令就立刻触发下游 SKU 检索，用异步流式把整体感知延迟压缩到远低于各阶段串行累加。

### Q6：自动化评估为什么用 judge 模型而不是 reward model？

两者不是一回事：

- **Reward model**：训练时给 RL 算法提供梯度信号，要求打分稠密、连续、可微分方向明确。
- **Judge model**：评测时给一批样本打可解释的分数，要求判断可靠、可复用、可指向具体错误类型。

现阶段系统核心瓶颈在 SFT 和数据质量，不是 RL 收敛。judge 的任务是产出"这条回答哪里错了、错在什么级别"这种结构化反馈，用来驱动纠错式 SFT 和 badcase 采样。

把 judge 和 reward model 合一的尝试在早期做过，典型问题是 judge 给出的分数在 RL 里过于稀疏（大部分样本都判错），训练信号根本起不来。拆开后 judge 专心做评测、reward model 在 SFT 把模型推到能被有效区分的区间后再接手，职责边界清楚很多。

judge 侧当前主力是 `deepseek-r1` 和 `doubao1.6-seed-thinking`，通过专门的 prompt engineering 给出多档评分 + 具体错误类型标注。

### Q7：Format Validator 为什么不用小模型？

跑过 `doubao1.6-nothink` 这类轻模型做 XML 格式校验，发现复杂嵌套场景下漏检率显著偏高——容易把结构错误的样本放过。切到 `doubao1.6-think` 和 `deepseek-r1` 这类具备推理链的模型以后漏检率明显下降。

这里省模型成本的代价是脏数据回流进训练集，后续纠错成本远高于 validator 本身的推理成本，不值得。

### Q8：Plan 模型与总结模型能不能合并成一个？

短期不建议合并：

- **职责解耦**：Plan 要产结构化 XML / JSON，总结要产自然语言回答，输出分布差异大，合并容易互相干扰。
- **迭代节奏**：Plan 迭代频率高、测试集稳定；总结更依赖生成质量评估，节奏完全不同。
- **调度灵活性**：Plan 产出后可以并行触发多路检索，合并成单模型就丧失这个 pipeline 并行能力。

长期目标是在多模态统一之后，让 Plan 与总结在更高抽象层统一（共享 VL 底座），但不是简单合成一个生成头。

### Q9：纠错式 SFT 里的 3K 条标签数据怎么构造？成本控制？

三步：

- **Badcase 采样**：从线上 query 里采 `select` 粒度错、`where` 幻觉等高频错误模式的样本。
- **双模型互检**：`deepseek-r1` 与 `doubao1.6-think` 分别给出修正版，不一致的交人工裁决，一致的进专家抽检。
- **粒度审计 prompt**：设计专门的"粒度审计专家" prompt，让大模型先判断"这条 query 需要 select 粒度是什么级别"，再生成修正 XML。

成本上大头是人工裁决环节（约 10%-15% 的样本），其余靠模型互检压。3K 条是把意图边界识别准确率从不稳定推到 98.07% 的关键阈值，再往上边际收益就明显下降了。

### Q10：整套系统上线以后，最容易踩的长尾问题是什么？

按踩坑频率排：

- **车型库细粒度解析错误**：车型边界 98.07% 准确率留出的 2% 误差集中在车系 / 车款 / 年款 / 海外版差异，细节见 [AI 选车车型库检索设计](file:///Users/bytedance/Documents/quartz-mygarden/content/note/bd/work/AI%20%E9%80%89%E8%BD%A6%E8%BD%A6%E5%9E%8B%E5%BA%93%E6%A3%80%E7%B4%A2%E8%AE%BE%E8%AE%A1.md)。
- **软偏好被当硬约束**："性价比高"、"颜值不错"这类被 Plan 翻译成 `where` 硬条件时会过筛选，需要专门 prompt 教模型分开"偏好"与"约束"。
- **过时价格 / 配置**：厂商库更新滞后导致的幻觉，靠权威数据源时效性校验处理，但不能完全消除。
- **低置信度时的兜底语气**：澄清模块如果做得生硬，用户体验反而比"没找到"更差，需要专门训一版澄清专用的语气模板。
- **多轮场景里的指代消解**：多轮改写模型承担，但改写失败时 Plan 会把上一轮约束丢掉，目前靠改写模型 SFT + GRPO 迭代压。

### Q11：多模态上线路径怎么排期？为什么不是 Plan / RAG / 总结同时上？

视觉能力进主链路的三个点——Plan、RAG、总结——看起来可以并行，实际排期里是强依赖的。上线顺序：**Plan 先行 → RAG 跟上 → 总结收尾**。

**Plan 先行**：`Plan 模型` 进化成 VL-LLM，先保证系统能理解用户上传的图片说了什么。这一步不动下游，输出仍然是结构化文本约束，图片里识别出的实体（车型 / 颜色 / 场景 / 对比对象）转成 query 改写或 where 条件，注入后续链路。这样下游的 RAG 和总结不需要任何改动就能从视觉输入中受益，是最低风险的切入点。

**RAG 跟上**：有了 Plan 的视觉理解，才能让检索层判断"这张图需要用多模态检索还是纯文本检索"。图片和视频作为可召回素材进入上下文，由 Plan 决定何时调用。这一步必须在 Plan 之后，否则 RAG 拿不到触发信号，多模态召回会变成无差别全开。

**总结收尾**：`总结模型` 升级成 VL 总结模型，支持图文混合输出。这一步延迟最久上线的原因是：图文混合输出的评测体系最不成熟，judge 模型本身还没稳——让 judge 模型学会"图文混合回答的相关性和美观度怎么打分"比单独升级模型本身更复杂。

三步并行的风险是：Plan 还不稳定时就让总结学图文输出，相当于在脏上下文里训生成，之前 `总结模型` 训练失败的剧本会在多模态上重演一次。必须按依赖顺序推。

### Q12：权威数据源的优先级策略具体怎么写？内部库、厂商库、网页三者冲突时以谁为准？

优先级不是一条硬规则，而是按 query 类型分层的查找表。

**强事实类 query**（价格 / 配置 / 参数 / 尺寸 / 动力 / 续航）：内部结构化库 > 厂商库 > 网页。内部库经过产品团队校对，口径最稳；厂商库时效性更好但偶有接口错误；网页最灵活但也最容易被营销话术污染。这类 query 网页数据只作参考，不作主答。

**评测 / 口碑 / 对比 query**：网页 > 厂商库 > 内部库。网页这时候反而是主力——用户要的就是多元观点，让内部库或厂商库替用户下结论不合理。

**热点 / 时效 query**（新车发布、OTA 升级、召回公告）：厂商库 > 网页 > 内部库。厂商库是官方第一口径，网页可以补充行业反应，内部库更新慢反而容易给出过时答案。

**冲突处理**：同一字段在不同源上不一致时，默认走更高优先级源，同时在 `总结模型` 的上下文里显式注明"另一源给出不同数值"。让模型有判断素材而不是让模型被动混搭。

这套策略的工程形态是每条检索结果都带 `source_type` 和 `confidence` 元数据，`Plan 模型` 在前置规划阶段根据 query 类型选权威源，后置融合阶段按优先级去重，不把同一事实从两个不同可靠性的源重复喂给总结。

### Q13：GRPO 第二次尝试怎么设计？和第一次失败的关键差异？

第二次 GRPO 要在 SFT 已经把基础能力推到 98.07% 的基础上做增量，目标不是让模型"学会"结构化输出，而是让它在"结构已经对的前提下，`select` 和 `where` 的语义选择更贴 query 意图"。

和第一次的关键差异有四点。

**起点不同**：第一次在几乎零正确率的模型上强化，reward 全是 0；第二次在已经稳定产出正确答案的模型上强化，reward 分布已经有区分度，GRPO 的相对比较才有梯度。

**Reward 信号分层**：第一次只用"整体正确与否"当 reward；第二次拆成三层——格式正确（0/1 硬性门槛）、`select` 字段匹配度（部分匹配连续分）、`where` 条件语义距离（基于属性层次与数值容忍度计算）。多层 reward 让 GRPO 在不同颗粒度上都有可比信号。

**Rollout 采样策略**：第一次均匀采样 query；第二次按 badcase 类型分桶采样，确保每个 group 里同时包含模型擅长和不擅长的样本，GRPO 的相对比较才有意义——全是容易样本或全是难样本的 group 会退化成噪声。

**KL 控制更紧**：第一次 KL 项几乎没限制，模型很快漂移到 reward hacking 路径（比如固定输出某个高分模板）；第二次 KL 系数显著加大，保证分布不偏离 SFT 后的基座太远，宁可慢一点也不要塌掉。

预期收益是把 `where` 条件生成准确率从当前水平再往上推 2-5 个百分点，重点是软偏好 vs 硬约束的区分。这件事 SFT 很难通过数据覆盖解决，必须靠 reward 引导。

### Q14：合成数据链路的稳定性是瓶颈之一，怎么判断合成数据"质量够用"？

合成数据不是"越多越好"，质量不到位时量反而是负资产。判断标准分三层。

**格式层**：XML Parser 可解析率必须 100%。这是硬门槛，解析不通过的样本直接拒绝，不进训练集。线上当前数据产出链路上这一层已经由 `Format Validator`（`doubao1.6-think` / `deepseek-r1`）保证。

**一致性层**：双模型互检一致率。`deepseek-r1` 和 `doubao1.6-think` 对同一 query 分别生成 Plan，XML 结构一致 + 关键字段一致的样本才进专家抽检池。当前这一层的一致率在 70%-80% 之间，不一致样本里大约有一半是"两个都对，表达不同"（正常多样性），另一半是"至少一个错"（必须人工裁决）。

**判别层**：用独立的 judge 模型对样本打多档分，只保留 judge 给出"强正确"的样本。这一层用 `deepseek-r1` 做 judge 时，产出率约 40%-60%，意味着合成的一半样本被判为有瑕疵。这个产出率本身就是衡量生产链路质量的重要指标——产出率如果突然下降，大概率是生成模型或 prompt 有回归。

**量的阈值**：经验值上，达到 98.07% 准确率需要 3K 条纠错样本，但这里面真正"难样本"（judge 多档分中间档）只占 30% 左右。难样本密度比总量重要——1K 条难样本 + 2K 条中等样本比 5K 条简单样本更有效。

所以合成数据质量够不够的判断不只是看数据量，而是看"格式正确率 + 双模型一致率 + judge 多档分分布 + 难样本密度"四个指标。任何一个掉下去都要先停数据扩张，回去修链路。

### Q15：这套系统里算法和工程怎么协同？模型迭代和线上部署的节奏怎么匹配？

整套系统有两条节奏不一致的迭代线：**模型迭代**（Plan / 总结 / 精排）频率高，周级甚至更短；**基础设施迭代**（召回索引、检索路径、数据管道、评测平台）频率低，月级。强行让两者对齐没必要，关键是让模型迭代不阻塞基础设施，也不被基础设施阻塞。

**接口契约先行**：每次模型升级前，先定 Plan 输出 XML schema、召回层 API、精排模型输入输出格式的契约。契约稳定的前提下，模型内部怎么换都可以——今天 `qwen3-30B-A3B`，明天换 `qwen3-72B`，线上链路不感知。这是模型能周级迭代而不炸的前提。

**影子链路 + 灰度**：新模型版本先在影子链路上跑一周，线上流量 mirror 过去，结果不进最终排序但记录对比数据。影子期间跑自动化评估，judge 模型打分合格后才切灰度 5%，再看一周线上指标。再放量到 50% 和全量。周期看着慢，但踩雷概率显著低于直接切流量。

**监控指标分层**：核心指标（车型边界准确率、精排 P90、综合得分）必须实时；次级指标（召回覆盖率、XML 格式正确率）每日看板；模型离线指标（judge 分数分布）周报。指标爆了按层级触发不同响应——核心指标掉了自动回滚，次级指标掉了触发 oncall 排查，离线指标异常进下周评审会。

**数据管道和模型解耦**：数据生产链路（多模型协同 + Format Validator + 拒绝采样）作为独立服务跑，产出物是版本化的数据集。模型训练从数据集拉数据，不直接挂链路输出。好处是数据链路出问题时模型训练能用上一版数据继续迭代，模型升级时数据链路也能稳定产出——两条线的故障互不传染。

**组织层面**：Plan / 总结 / 精排 / 召回 / 评估最好各有专人，但必须有一个系统架构师统筹所有接口契约和指标口径。典型陷阱是每个模块都在本模块指标上迭代得很好，但合起来线上指标反而回退——根因往往是模块间接口或数据口径悄悄漂移了，需要有人专门看住这些接缝。

## 小结

这套系统真正的问题从来不是某个模型选错或某个 prompt 没调好，而是职责边界不清、链路拆得太碎、训练与评测闭环不稳。把主线收回来——Plan 中心化、RAG 拆三段、数据与评测先于 RL、多模态进主链路、车型库检索作为关键底座——大部分看起来互不相干的坑会一起变浅。

剩下的工程化工作是把 98.07% 再往上顶、把 91ms 再往下压、把澄清兜底做得更体面，以及把多模态真正接进主链路。这几件事做扎实以后，今天这套系统的上限就会被重新定义。
