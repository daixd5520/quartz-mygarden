# 场景

选车这个场景有几个绕不开的特点：

- 单表结构，不需要 join。
- 筛选和排序的逻辑复杂，用户偏好描述常常是软性的（"续航无所谓"、"动力强一点"）。
- Schema 比较大，直接塞进 prompt 会炸上下文。

# Schema Linking

语义相似度匹配的基本流程：找问题的答案最可能落在哪张表、哪一列。

- 遍历 schema 里所有表，算表名和问题的相似度（问题 embedding vs 表描述 embedding）。
- 对每张表再算问题和所有列名的相似度（问题 embedding vs `列名 + 列描述` 的 embedding）。

# 系统设计

SQL 处理不了"动力强一点但续航无所谓"这种软性偏好，所以我们直接用 XML 描述选车需求：

- `<select></select>`：需要查出的重要属性。
- `<where></where>`：过滤条件，格式 `过滤属性名##过滤值##必要程度`，例如 `车辆价格##[10, 15]##必要`。
- `<order></order>`：排序条件，格式 `排序属性名##排序类型##必要程度`，例如 `百公里加速时间##ASC##必要`。
- `<group by></group by>`：分组条件，用于"同车系不同限制"这种场景。
