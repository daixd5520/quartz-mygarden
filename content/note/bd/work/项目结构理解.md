这是我读 `motor.nlp.select_car` 这套服务时自己整理的"地图"，留给以后自己快速定位代码用。和 [项目](项目.md) 的区别是：那边是对外可交付的 reference，这里是工程实现上的 why。

## 技术栈

| 技术 | 选型 | 备注 |
| --- | --- | --- |
| RPC | Apache Thrift + Euler | Euler 是字节内的 Thrift server |
| 并发 | Gevent | IO 密集型，协程扇出比线程池更合算 |
| 缓存 | Redis | 主要缓存 query analysis 与召回结果 |
| 存储 | SQL / Hive | 离线看板、bad case 捞取 |
| PSM | `motor.nlp.select_car` | 字节内服务标识 |
| 召回 | ES 与 VikingDB | 线上车系/车款走 VikingDB，ES 代码留着但没用 |

### ES 和 VikingDB 在这个项目里的定位

| | Elasticsearch | VikingDB |
| --- | --- | --- |
| 本质 | 基于 Lucene 的全文检索引擎，后补的向量能力（`dense_vector` + HNSW） | 字节火山引擎出品，原生向量库 |
| 适合的场景 | 既搜关键词又要语义混合召回时一站式解决 | 亿级以上向量、对延迟/吞吐敏感的推荐场景 |
| 本项目里 | 代码写了但初始化被注释掉，线上不跑 | 车系/车款的主召回通道 |

实践里没走 ES 的原因很直接：车系车款是有限的实体集合，向量召回加人工规则已经够用，没必要再维护一套倒排。

## 基本概念

- `carBase`：车系（比如"Model Y"）
- `carModel`：车款（比如"Model Y 2024 长续航后驱版"）

车系是用户大部分提问的粒度，车款主要用于报价、配置等精确查询。

## `schema_retrieve`：从 params schema 里给 LLM 挑 TopK

召回主体逻辑：

~~~python fold file:plan.py->schema_retrieve
def schema_retrieve(question_query):
    """为大模型规划（plan）准备 schema。

    Select 侧：从 params_schema_config 里召回 TopK 个与 query 最相关的属性 schema，
              拼到 prompt 的 <select>/<order>。
    Where 侧：返回固定的 where-schema（<where>/<group_by>），不做召回。

    返回：
    - select_schema: 默认 select schema + TopK 召回拼接
    - where_schema: 固定 where schema
    - select_retrieve: 仅 TopK 召回的 schema_select 拼接（调试用）
    - extra_result: TopK 明细 + 中文字段到 schema 的映射（供下游字段映射/聚合属性展开）
    """
    select_schema = default_shema_select
    where_schema = default_shema_where
    select_retrieve = ""
    extra_result = {}

    question_query = question_query.lower()

    default_select_params = [
        "car_price_agg", "car_appearance_agg", "car_interior_agg",
        "car_space_agg", "car_maneuverability_agg", "car_power_agg",
        "car_endurance_agg", "car_comfort_agg", "car_intelligentization_agg",
        "car_safety_agg", "car_energy_consumption_agg",
    ]
    # 兜底/过大集合，不参与召回
    unuse_params = ["car_introduction_agg", "car_params_agg"]

    topk = 10

    # 1) 构建候选池 + 中文字段映射（供下游把 LLM 输出的中文字段映射回 params_name/type）
    params_schema_config_list = list()
    params_name_2_schema_info = dict()
    for param_name, param_item in params_schema_config.items():
        param_cn_name = param_item["params_cn_name"]
        params_name_2_schema_info[param_cn_name] = param_item

        if param_name in default_select_params or param_name in unuse_params:
            continue
        params_schema_config_list.append(param_item)

    print("input params_schema_config_list size::: {}".format(len(params_schema_config_list)))

    # 2) 批量构造 query/title/docs 供打分
    query_batch = [question_query] * len(params_schema_config_list)
    param_name_batch = [item["params_name"].lower() for item in params_schema_config_list]
    schema_relevance_batch = [item["schema_relevance"].lower() for item in params_schema_config_list]

    # 3) 两路分：QA no-answer 相关性分 + 字符级 BM25
    bm25_schema_relevance = BM25(schema_relevance_batch)

    ans_s_time = time.time()
    for _ in range(10):
        _, summary_model_results = get_summary_info(query_batch, param_name_batch, schema_relevance_batch)
        if len(summary_model_results) > 0:
            break
        else:
            print("get_summary_info failed, try again")
    ans_e_time = time.time()
    print("ans_cost_time::: {}".format(ans_e_time - ans_s_time))

    ans_score_list = []
    bm25_score_list = []
    for idx, ans_result in enumerate(summary_model_results):
        # answer_score = 1 - no_answer_score，越大越相关
        ans_score_list.append(1 - ans_result.no_answer_score)
        bm25_score_list.append(bm25_schema_relevance.score(query_batch[idx], idx))

    # 4) min-max 归一化后等权融合
    ans_score_list = min_max_normalize(ans_score_list)
    bm25_score_list = min_max_normalize(bm25_score_list)

    for idx in range(len(params_schema_config_list)):
        params_schema_config_list[idx]["answer_score"] = ans_score_list[idx]
        params_schema_config_list[idx]["bm25_score"] = bm25_score_list[idx]
        params_schema_config_list[idx]["rank_score"] = (
            params_schema_config_list[idx]["answer_score"]
            + params_schema_config_list[idx]["bm25_score"]
        )

    # 5) 排序、取 TopK、拼 select_schema
    params_schema_config_list = sorted(
        params_schema_config_list, key=lambda x: x["rank_score"], reverse=True
    )

    dump_json(
        params_schema_config_list,
        "/cloudide/workspace/motor_dynamic_summary/eval_data/params_schema_config_list.json",
    )

    top_schema_config_list = params_schema_config_list[:topk]
    select_retrieve = "\n".join([item["schema_select"] for item in top_schema_config_list])
    select_schema += "\n" + select_retrieve

    extra_result = {
        "top_schema_config_list": top_schema_config_list,
        "params_name_2_schema_info": params_name_2_schema_info,
    }

    return select_schema, where_schema, select_retrieve, extra_result
~~~

几个工程上值得留意的点：

1. BM25 这里传入的是字符串列表，拆分粒度是字符级而不是词级，对中文短 query 其实比 jieba + 词级 BM25 更稳。
2. `answer_score = 1 - no_answer_score`，用的是 search plugin 的 QA 模型。它和 BM25 刚好一语义一字面，融合起来冗余度低。
3. 归一化用 min-max 而不是 softmax，是因为两路分不需要概率解释，只要 rank 顺序正确。
4. 等权求和是最朴素的融合，线上真要调优可以改成 learned weights 或者 rank fusion（RRF），目前没看到这条路径的 AB。

## 迭代时会踩的坑

- 改 `params_schema_config` 后要同步检查 `default_select_params` / `unuse_params`，不然新加的字段可能被兜底名单抢占了 TopK 名额。
- `schema_retrieve` 打 dump 的路径 `/cloudide/workspace/motor_dynamic_summary/eval_data/` 是调试残留，线上 pod 不一定可写，观察是否有 warning。
- `CarEsRecallService` 初始化被注释只是当前策略，如果未来需要做关键词+语义 hybrid，直接取消注释 + 对齐 schema 即可，代码是完整的。
