# AI 选车 Agent 业务架构

这篇原本是一组 AI 选车 agent 架构图的 onepage 存档。现在把图里的核心信息补成文字版，方便后续检索、复盘和继续拆子模块文档。

![[ai car agent-1.png]]

这张图对应的是 agent 任务编排总览，重点不在模型，而在任务如何被接入、落库、调度、执行、回传和通知。

- 接入层承接用户侧发起的异步任务，请求里至少带 `userId`、`vPhone`、`imID` 这类身份标识，并暴露查询进度、取消任务等接口。
- 接入网关负责鉴权、限流和链路追踪，典型能力是鉴权与配额控制、`Trace` 注入、日志与 `SpanID` 打点，以及请求维度的重试、查询、取消。
- 主 Agent 本体只做任务编排，不直接承担所有执行逻辑。图里把 `SpawnTool`、`Controller`、`TaskManager`、`TaskStore` 分开，就是为了把“生成计划”“调度执行”“状态存储”三件事解耦。
- `Task Store` 采用 MySQL + Redis 的双存储。MySQL 持久化任务元数据、历史与偏好，Redis 承担热缓存、任务队列和短生命周期状态，典型是 `taskId -> status`、`taskId -> progress` 这类高频读写。
- 消息层通过 BMQ 做异步解耦，至少有两条主题：一条把 `SubAgent` 任务派发到执行池，一条把执行结果送到 `NotifyRouter` 做结果推送。
- 执行层是 `SubAgent Worker Pool`。每个 worker 从消息队列消费任务，执行子任务，把结果写回 `TaskStore`，必要时再把阶段性事件写回 BMQ。图里强调 `yield`、结果回填、失败日志、Redis 分布式锁和 checkpoint，说明执行层默认按长任务和可恢复任务设计。
- 内部运维管理不是附属能力，而是运行闭环的一部分。图里单独列了超时巡检、卡死恢复（`StuckRecovery`）和运维 API，意味着这套系统默认接受“长任务会卡住、分布式执行会丢状态、需要后台介入”的现实。
- 通知推送层统一承接 `IM`、`Push`、站内信之类触达通道，核心不是多发一个消息，而是把“任务完成 / 失败 / 需要用户补充信息”的状态收敛成统一出口。

这张图给出的判断很明确：AI 选车 agent 不是一个同步问答框，而是一套带状态机、消息总线、任务仓储和恢复机制的异步系统。

## 业务架构 onepage

![[ai car agent-2.png]]

这张图是五层架构图，自上而下分成业务层、架构层、模型层、数据层和工具层。它的价值不在于把所有名词摆上去，而在于把职责边界划清楚。

- 业务层承接具体业务入口，图里列了选车 agent、用车 agent、智能导购、IM 智能客服、智能外呼、二手车 agent、新车 agent。这些入口共享一套底层能力，但不会共享一套 prompt 就结束。
- 架构层是通用能力层，包含 `tools`、`skills`、`memory`、`RAG`、通用搜索、`Func6` 之类编排与调用能力，以及数据管理、效果评估、模型训练、模型部署、外呼能力、ASR、OCR。这一层决定的是“怎样组织能力”，不是“用哪个模型”。
- 模型层按模态拆分，文本模型包括 `qwen3.5`、`deepseek v4`、`豆包 1.8`、`kimi2`；多模态模型有 `qwen vl` 和 `paddle-ocr`；omni 语音侧有 `qwen omni` 与 `VAD`。这个分层说明系统不是押单模型，而是按任务类型组合。
- 数据层分成两块：一块是业务数据，如车型库、价格体系、使用说明书、独家文章、实测数据、故障知识库；另一块是底层存储，如 MySQL、Redis、Viking。前者决定 answer 有没有事实基础，后者决定系统能不能稳定跑。
- 工具层把 AI coding、模型开发工具和框架层放在最下方，说明工程效率工具与线上运行框架被当成基础设施，而不是团队个人习惯。

如果把这张图压成一句话，就是：上层业务不直接碰模型，下层模型不直接碰业务，真正的复用点在架构层和数据层。

![[ai car agent-3.png]]

这张图对应 `4.1.1 RAG 管理系统`，把知识接入、处理流水线和检索服务拆成了一条完整链路。

- 数据输入分三类：结构化数据（车型库、价格、参数）、非结构化数据（文章、评价、手册）、实时数据（行情、促销、库存）。这个拆法很实用，因为三类数据的接入频率、切分方式和更新策略都不一样。
- 处理中枢先做文档解析，支持 `PDF / HTML / 表格`，再做文本分块与语义切分，然后生成向量 embedding，最后构建混合索引。
- 检索服务同时保留语义检索和关键词检索，两路结果进入混合检索，再经过重排序输出结果。这里写得很直白：不能把向量检索当成全部答案，BM25 这类关键词路径仍然是必要底座。
- 图下方的功能说明补了四个工程点：统一知识接入、混合检索 + `Cross-Encoder` 重排、增量更新与全量重建并存、Recall@K / MRR / NDCG 这类检索评测体系内建。

这张图里最重要的不是“做了 RAG”，而是把 RAG 当成一个可运营的系统：有接入、有构建、有评测、有更新，而不是用户问了才临时去搜。

![[ai car agent-4.png]]

这张图对应 `4.1.3 Memory 管理系统`，核心是把记忆明确分成短期、中期、长期三层，而不是笼统地说“系统有记忆”。

- 短期记忆存当前对话上下文，落在 Redis，目标是低延迟和 TTL 自动过期。
- 中期记忆存跨会话偏好和交互历史，图里给的方案是 MySQL / MongoDB 这类文档或关系存储，重点是可更新、可筛选、可按用户聚合。
- 长期记忆存用户画像和持久化知识，落在图数据库，候选是 `Neo4j` / `NebulaGraph`。这里的直觉是对的：长期记忆往往不是一张扁平表，而更像关系网络。
- 记忆检索与召回按当前语境触发，支持时间衰减、重要性加权、相关性排序。这意味着记忆不是全量塞回上下文，而是按使用场景做选择性注入。
- 记忆更新与淘汰是系统默认能力。图里明确写了自动更新、偏好变化及时同步、`LRU + 重要性评分` 的混合淘汰策略，说明设计目标不是“记得越多越好”，而是“记住有用的、忘掉过时的”。
- 隐私与安全被单独列出来，包含加密存储、用户主动删除个人记忆、满足数据隐私合规。这一点很关键，因为记忆系统一旦进生产，隐私问题不是附加项。
- 技术选型表也很实在：短期记忆用 `Redis Cluster`，中期用 `MongoDB`，长期用 `Neo4j / NebulaGraph`，记忆向量化复用 `Viking`，与 RAG 共用向量检索基础设施。

这张图背后的系统观念是：Memory 不该只是“把聊天记录丢给模型”，而是一套分层存储、分层召回、可淘汰、可审计的用户状态系统。

![[ai car agent-5.png]]

这张图是模型上线流程，虽然看起来简单，但把线上模型治理最容易漏掉的几步全写出来了。

- 起点是模型训练完成，随后进入自动化评测。
- 评测达标后才进入模型注册、镜像构建和灰度发布，灰度比例按 `1% → 10% → 50% → 100%` 逐步放量。
- 灰度之后不是直接算完成，还要经过线上监控，再判断“效果达标？”。
- 达标才进入全量发布，不达标则自动回滚。

这条流程真正想说明的是：模型上线不是“训完就发”，而是默认带着评测门槛、注册流程、分阶段灰度、在线观测和自动回滚能力。这和普通后端服务发版很像，只是这里多了一层模型效果门槛。

![[ai car agent-6.png]]

这张图对应 `4.3.1 Agent 框架`，把业务闭环、Bot 职责分层、能力层、架构层、数据层和基础层一起画出来了。

- 业务层画的是一条典型转化链：选车用车 → 留资 → 成交。图里用小懂、导购、网销三个节点表达，意思不是只有三类 bot，而是 agent 最终要服务实际业务漏斗。
- 应用层把 bot 分成 `小懂Bot`、`导购Bot`、`新车Bot`、`二手车Bot`。它们共享 `Memory`、`RAG`、`Plan`、`Summary`、`Supervisor` 这些公共骨架，但也保留专属模块，比如 `Intention` 或多个 `sub` 子能力，说明系统既复用又允许业务特化。
- 触达通道包括 `IM`、企微、AI 外呼、短信、Push`。这意味着 agent 不是单会话容器，而是跨渠道一致运行。
- 能力层把种草、转化、多模态三类能力拆得很细：种草包括榜单、资讯、实测、点评、口碑、参配、懂车、评测；转化包括比选、讲解、车况、金融、政策、优惠、推荐、身份；多模态包括 ASR、OCR、TTS 等。图的意思很清楚：agent 上层的“会聊”只是表象，真正决定体验的是底下这批可调用能力。
- 架构层列了 `AGENT` 框架、可视化编排、Prompt/PE、低代码复用、`Trace`、`Memory`、`RAG`、`Skills`、`MCP Tools`、`A2A`。这说明系统是按“能力可组合”来建，而不是每个业务线各写一套 agent。
- 数据层包括用户画像、图谱、汽车知识库、Agent 对话历史、人工标注、训练样本、行为序列、自然人映射。这里把训练数据和用户数据放在一起，是因为 agent 体系天然是数据闭环系统。
- 基础层强调训练与推理基建：profiling、调度、混合精度、算子优化、并行、量化、推理引擎、KV cache、资源调度、模型管理、负载均衡、数据平台等。图右侧还单独列了治理维度：稳定性、速度、成本、效率、安全合规。

这张图最后落到的是一个很现实的结论：Agent 框架不是“多套 bot + 一个大模型”，而是业务漏斗、渠道触达、能力编排、训练数据、推理基建和治理体系一起组成的操作系统。

## 文字版小结

把六张图合起来看，这套 AI 选车 agent 业务架构大致可以压成四条主线。

- 第一条是任务系统主线：接入、鉴权、任务编排、消息总线、执行池、状态存储、通知回传，决定系统能不能稳定跑长任务和异步任务。
- 第二条是能力系统主线：RAG、Memory、Plan、Summary、多模态、技能与工具调用，决定系统到底能做什么。
- 第三条是模型与数据主线：文本模型、多模态模型、业务数据、用户数据、训练样本、评测闭环，决定系统效果有没有上限。
- 第四条是工程治理主线：灰度发布、自动回滚、稳定性、成本、安全合规，决定系统能不能上线、能不能长期维护。

如果后面继续拆文档，最值得单独展开的几个点是：`Task Store + BMQ` 的任务调度机制、RAG 的索引与评测闭环、Memory 的分层召回策略，以及多 Bot 共享 Agent 框架下的能力复用边界。
