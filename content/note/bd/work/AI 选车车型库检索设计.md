# AI 选车车型库检索设计

车型库检索是 AI 选车问答系统里最值得重兵投入的基础设施。许多看起来属于 `Plan 模型` 或 `总结模型` 的问题——查不到车、查到不相关的车、检索结果和回答口径对不上——追根究底都能落回这里。

这篇文档从系统架构起笔，依次拆解 `Plan-2 / ToolPlan`、召回层、排序层、应用层、线上指标与迭代节奏，以及"车场景和传统电商搜索有什么不同"这类容易被忽略的业务判断。系统级背景可以参考 [AI 选车问答系统问题拆解与演进方案](file:///Users/bytedance/Documents/quartz-mygarden/content/note/bd/work/AI%20%E9%80%89%E8%BD%A6%E9%97%AE%E7%AD%94%E7%B3%BB%E7%BB%9F%E9%97%AE%E9%A2%98%E6%8B%86%E8%A7%A3%E4%B8%8E%E6%BC%94%E8%BF%9B%E6%96%B9%E6%A1%88.md)。

## 1. 总体架构

车型库检索整条链路分四层：`Plan-2 / ToolPlan` 解析 query → 召回层（char 粒度倒排 / 向量召回 / 选车倒排）→ 排序层（双塔粗排 + 单塔精排）→ 应用层（结构化输出 + 综合得分 + 澄清兜底）。四层各自可评测、各自可替换，不共享生成目标。

![[微信图片_20260412220851_18_9.png]]

这套架构的核心工程取舍：

- **检索与生成解耦**：`Plan-2` 不直接回答问题，只把 query 翻译成可执行的结构化约束，后面的召回和排序独立迭代。生成侧的任何 prompt 变动不污染检索链路。
- **召回层多路并行**：不赌单一召回路径。`char` 粒度适合短 SKU Title 实体识别兜底，向量召回覆盖语义改写，倒排覆盖结构化精确匹配，三路通过配额合并。
- **排序层先粗后精**：粗排在大池子里做低成本筛选，精排再做细粒度相关性判断，避免把昂贵的单塔模型铺在所有候选上。
- **应用层负责兜底体面**：召回和排序都不达标时进入澄清流，不硬答也不机械说"没找到"。

## 2. Plan-2 / ToolPlan：把 query 翻译成结构化约束

`Plan-2` 是 `Plan 模型` 在车型库子链路上的具体形态——主力 `qwen3-30B-A3B`，SFT + 纠错式数据训练。它和 `Plan 模型` 是同一模型在不同阶段的叫法，职责不是直接给答案，而是把 query 拆成可执行的结构化约束。

![[微信图片_20260412220909_19_9.png]]

### 2.1 两类关键输出：车型描述边界 + 筛选条件

`Plan-2` 产出两类硬对象。

**车型描述边界**决定品牌 / 车系 / 车款识别到哪一层。最新评测上车型边界识别准确率约 **98.07%**（1403 条评测 case）。这个数字直接决定下游召回能不能拿到对的实体，也是整套系统为数不多达到"可上线"口径的指标。

**筛选条件**覆盖价格、驱动方式、动力类型、配置、用途等约束。当前线上 `where` 侧仍然会出现车系 / 车款解析错误，是后续迭代主方向。

### 2.2 XML 而不是 SQL

早期尝试过 Text2SQL，在多表关联和复杂嵌套过滤下 LLM 生成准确率只有约 **76%**，括号 / 引号类语法错误占相当比例。换成 XML 以后：

- `<select>`、`<where>`、`<order>`、`<group_by>` 四个标签把查询指标和过滤条件解耦，生成幻觉明显下降。
- 有专门的 XML Parser 做硬格式校验，格式错的样本直接在数据产出阶段被拒掉，不流进训练集。
- 对选车场景高频的 `order by 销量 / 热度`、`group by 车系` 表达友好。

500+ query 自评下 XML 输出未发现格式错误，同期 SQL 输出的格式错误率远高于可接受阈值。这是当前这套设计站在 XML 一侧的直接依据。

```xml
<plan>
  <select>
    <field>model_name</field>
    <field>msrp_price</field>
    <field>nedc_range</field>
  </select>
  <where>
    <condition field="vehicle_type" op="eq" value="SUV"/>
    <condition field="energy_type" op="eq" value="纯电"/>
    <condition field="msrp_price" op="between" value="[8, 12]"/>
    <condition field="status" op="in" value="['在售','即将上市']"/>
  </where>
  <order field="sales_score" direction="desc"/>
  <group_by field="series_id"/>
</plan>
```

### 2.3 Schema 注入：InputDataSchema 的 Top30 检索

车型库属性总数在几百以上，不可能每次都全量塞进 prompt。走两步：

1. 对 query 做属性名相关性检索，取 Top30 属性拼成 `InputDataSchema`，分 select 与 where 两部分注入。
2. 在每个属性描述里明确单位和标准输出格式，比如价格单位"万元"、区间表达 `[10, 15]` 代表 10-15 万、开闭口径统一。

这样做的好处是 prompt 长度可控（token 控在 1500 以内），同时让 `Plan-2` 在看不全 schema 的前提下依然能稳定输出结构化查询。

### 2.4 模糊语义到结构化区间的映射

典型 query："10 万左右的 SUV"。三层配合处理：

- **Schema 层**：`msrp_price` 字段描述里写清楚单位与区间格式。
- **模型层**：`qwen3-30B-A3B` 的推理能力负责把"左右"转成浮动区间。
- **规则层**：对"10 万"这类单点价格走数值解析 + ±20% 容忍度展开（`[8, 12]`）。

线上 `where` 侧当前的主要残余问题不在价格区间，而在车系 / 车款名细粒度解析——这是下一轮训练集要重点扩充的方向。

### 2.5 纠错式 SFT：怎么把 98.07% 磨出来

`Plan-2` 的训练路径经历过一次完整的"GRPO 失败 → 回退 SFT"复盘。

GRPO 第一次尝试时，初始模型在 `select` 粒度、`select` 隐形决策指标、`where` 条件幻觉这类硬问题上几乎不产出可判为正确的样本，reward 极其稀疏，训练跑不起来。结论很直接：**RL 适合做"80 到 95"，不适合做"0 到 60"**。

回到 SFT 路径以后，高频错误类型收敛到六个：

- `select` 粒度过细：倾向选类别属性而不是具体指标。
- `select` 粒度过粗：选出聚合字段，无法回答具体问题。
- `select` 隐形决策指标缺失：query 暗含的关键决策维度没被带出来。
- `select` 核心指标缺失。
- `where` 过筛选：把软偏好当硬过滤。
- `where` 错筛选 / 条件幻觉。

针对这六类做专门的"粒度审计专家" prompt，配合 3K 条人工标注纠错数据做 SFT，把意图边界识别准确率从不稳定状态推到 **98.07%**。继续往上顶靠强化学习，这时 reward 信号已经密了很多，GRPO 才有机会接手。

## 3. 召回层

![[微信图片_20260412221112_22_9.png]]

### 3.1 三路并行：char / 向量 / 选车倒排

**Char 粒度倒排**服务 SKU Title 短、实体识别易错的场景。字符级倒排比分词更稳——"腾势 Z9GT"、"AITO 问界 M9 先行版"这类新车 / 别名，分词器很容易切错，字符级至少保证 n-gram 上可命中。线上这一路是实体识别失败时的硬兜底。

**向量召回**以 `qwen3-0.6B Embedding` 和 `BGE Embedding` 为主力，覆盖语义改写与相似表达。"适合家用的中型 SUV"、"年轻人第一辆车"这种描述性 query，倒排路几乎没用，必须靠向量召回。模型选 0.6B 级别是工程权衡——线上 QPS 压力下，更大的 embedding 模型虽然更准但延迟不能接受。

**选车倒排**走结构化索引。`Plan-2` 输出的 `where` 条件直接翻译成倒排查询，做属性约束的精确匹配。这一路是"价格 10-15 万 + 纯电 + 三厢"这类硬约束 query 的主力路径。

### 3.2 Quota Snake Merge：不靠简单并集

多路合并最常见的错误做法是取并集后依赖后续排序。问题在于：

- 向量召回有时候会返回大量"看起来相关但实际跑偏"的候选，把倒排的精确结果挤出 Top-K。
- 字符级倒排在某些 query 下会产出海量低相关结果，淹没向量的长尾补位。

**Quota Snake Merge** 给每一路分配配额，按蛇形顺序依次取：第一轮从每一路取第 1 名，第二轮每一路取第 2 名，依次类推，直到填满候选池。遇到某一路配额用尽时跳过，优先保证精确匹配路径的权重。

这样做的直接收益是精确命中永远排在最前，向量补语义长尾，char 兜底实体错误，三路互不抢占。线上调参留给每路的配额比例，而不是排序权重。

### 3.3 状态敏感：在售 / 停售 / 即将上市

召回层必须处理车型状态。一条 "10 万 SUV" query 如果召回里混着大量 2015 年的停售车型，后面排序做得再好也救不回来。

处理方式是在倒排层和向量层分别加状态过滤：

- **硬过滤**：非用户主动问停售车型时，默认只召回在售、即将上市、未上市的车型。
- **软降权**：停售但仍有讨论热度的车型保留在候选池，但在综合得分里拉低权重，避免"老车占位"。

状态处理不是召回后做的 post-filter，而是召回阶段内嵌的索引结构。这和普通电商搜索的"上架 / 下架"二元模型不一样——车型有更复杂的生命周期状态，专门建模才稳。

## 4. 排序层

![[微信图片_20260412221112_23_9.png]]

### 4.1 粗排：双塔模型，低成本高吞吐

粗排用 `BGE Reranker` / `qwen Reranker` 这类双塔模型，承担从大候选池（召回后 500~1000 条）压到精排输入池（Top 50~100）的任务。这一层选型的核心是成本和延迟：双塔模型的 query 向量和 doc 向量可以分别预计算，线上只做一次点积，P99 延迟在十几毫秒量级。

### 4.2 精排：单塔 + LLM 蒸馏 + Level-Wise Relevance

精排是 query 和 doc 共同进入模型做深度交互的单塔结构，关键设计是 **LLM 蒸馏 + Level-Wise Relevance**。

**5 档相关性标注**：Strong Relevant / Relevant / Partial Relevant / Irrelevant / Strong Irrelevant。不用 0/1 二元相关性，因为选车场景里很多候选是"相关但不是最好"，用 5 档能保留更丰富的梯度信息。

**LLM 打标 + 小模型蒸馏**：`deepseek-r1` 和 `doubao1.6-seed-thinking` 作教师模型给候选打 5 档标签，然后把相关性判断蒸馏到 `qwen3-1.7B` 单塔学生模型。这样做的目的是把大模型的判断能力压缩到一个延迟可控的小模型里——端到端 P90 约 **91ms**，满足线上实时问答的延迟预算。

**Hard Case Mining**：精排判错的 case 采样回训练集做 finetune，重点回捞"高相关但排在后面"和"低相关但排在前面"两类样本。这是持续抬上限的主要手段。

### 4.3 车场景相关性和传统电商的差异

普通电商搜索相关性模型直接套到选车场景会栽跟头，原因有三：

- **标签少但判定难**：车 SKU 的属性标签数量比普通电商商品少，但 query 里的复合软约束极重。"20 万内性价比最高的纯电 SUV" 同时包含价格、能源类型、车身类型、性价比这种主观指标，纯相关性模型处理不了主观偏好。
- **对比需求极大**：选车 query 里隐含的"和什么比"天然存在。"比特斯拉 Model Y 便宜的同级车"这种 query，普通电商相关性模型没有对比能力。
- **状态敏感度高**：电商商品二元上下架够用，车型要区分在售、停售、即将上市、未上市四态以上，还有年款版本差异。

这决定了选车场景的精排必须走单塔 + LLM 蒸馏路线，而不是直接复用通用电商 reranker。

## 5. 应用层

![[微信图片_20260412221112_24_9.png]]

### 5.1 结构化输出：口径明确到车款级

应用层输出给下游的结果不是一串 SKU ID，而是带粒度信息的结构化响应：品牌 / 车系 / 车款三层都明确标注到哪一层，`总结模型` 据此组织回答语言。

比如 query "蔚来 ET7 多少钱"，应用层返回的不只是一个 SKU 列表，还包括"这是车系 ET7 下的 X 个车款"的粒度标签。`总结模型` 据此决定回答要不要展开到车款，还是按车系级给一个价格区间。这避免了"用户问车款价格，模型答了车系起售价"这类常见口径错位。

### 5.2 综合得分：相关性 + 业务指标

应用层最终排序不只看模型分。线上公式：

$$\text{composite\_score} = 0.6 \cdot \text{norm\_tag} + 0.3 \cdot \text{norm\_sale} + 0.1 \cdot \text{norm\_hot}$$

三个分量归一化后加权：

- `norm_tag`：精排模型给出的相关性分，权重 0.6。
- `norm_sale`：销量归一化分，权重 0.3。反映车型在市场上的真实接受度。
- `norm_hot`：内容热度归一化分，权重 0.1。来自站内讨论、搜索、浏览等行为数据。

权重 `0.6 / 0.3 / 0.1` 不是拍脑袋定的，是线上 A/B 反复调出来的经验值。主要解决"搜奔驰结果里排在前面的是非主流车款 / 低销量改装版"这类纯相关性模型解决不了的问题。

销量和热度的引入也是选车场景和纯技术文档检索（比如 RAG on Docs）最大的区别——用户问"10 万 SUV"时，他要的是市面上真实好卖的那几款，不是数据库里"最相关"的那几款。

### 5.3 澄清模块：低置信度时的兜底

召回和排序置信度都不够时，硬答会直接给用户体验挖坑。应用层在这种情况下进入澄清流，由 `总结模型` 生成两部分内容：

- **缺失信息描述**：具体缺哪个维度的约束，价格？车身类型？能源类型？
- **可选近似候选**：基于当前弱约束能召回的 Top-N 候选，让用户从中挑或者补充信息。

澄清模块的关键是语气。生硬一句"信息不足请补充"比直接说"没找到"体验更差，需要专门训一版澄清专用的语气模板，让模型用友好、专业的语气引导补充信息。这一层已经在线上 DONE 列表里闭环。

## 6. 线上指标与迭代节奏

![[微信图片_20260412221112_25_9.png]]

### 6.1 核心指标

落地过程里持续追踪的指标：

- **车型边界识别准确率**：98.07%（1403 case）。
- **`where` 条件生成准确率**：当前仍是主要提升空间，尤其在车系 / 车款细粒度上。
- **精排 P90 延迟**：91ms。
- **XML 格式正确率**：500+ query 自评下未发现格式错误。
- **召回 Top-K 覆盖率**：三路并行 + Quota Snake Merge 下，主流 query 召回覆盖率显著高于单路方案。

### 6.2 排期锚点

- **2 月 9 日**：`char` / `embedding` / 倒排三路召回打通，补齐在售 / 停售 / 即将上市等关键数据状态。
- **2 月 13 日**：精排进入领域化训练阶段，开始 LLM 蒸馏与 Hard Case Mining。

- 车型别名（新车 / 海外版 / 国内版）召回。
- 在售 / 停售 / 即将上市 / 未上市的状态处理。
- 澄清模块的语气专项训练。
- 综合得分权重 A/B 调参。
- Schema Top30 检索替换全量属性塞入。

## 7. 长尾问题与后续方向

线上踩坑频率排序：

- **车系 / 车款细粒度解析错误**：98.07% 留出的 2% 误差集中在新车别称、年款版本、海外版 / 国内版，靠 char 粒度兜底但 `Plan-2` 侧需要持续喂数据。
- **软偏好被当硬约束**："性价比高"、"颜值不错" 被 `Plan-2` 翻译成 `where` 硬条件时会过筛选，专门 prompt 教模型分开"偏好"与"约束"。
- **过时价格 / 配置**：厂商库更新滞后导致的幻觉，靠权威数据源时效性校验处理，但不能完全消除。
- **低置信度时的兜底语气**：澄清模块生硬比"没找到"更差，需要专门训语气模板。
- **多轮场景里的指代消解**：多轮改写模型承担，改写失败时 `Plan-2` 会丢上一轮约束，需要改写模型 SFT + GRPO 迭代压。

后续主要演进方向：

- **多模态召回**：用户上传图片问"这车是什么"、"有没有类似的车"，需要 VL-LLM 直接进入召回层做以图搜车。
- **对比类 query 专用链路**：高频对比类 query（"A 和 B 哪个好"）当前由 `总结模型` 兜底，后续考虑在应用层加专门的对比渲染。
- **Plan-2 → Plan 合一**：长期看 `Plan 模型` 和 `Plan-2` 应当在多模态统一之后合并到一个理解层。

## 8. 面试拷打题

### Q1：车场景召回为什么要三路并行，不能只留向量召回？

向量召回单独用在三类 query 上会栽跟头：

- **实体识别失败**："腾势 Z9GT" 这类新车 / 别名，embedding 如果训练时没见过会召回一堆不相关车型。字符级倒排至少能在 n-gram 上命中。
- **硬约束 query**：价格 10-15 万 + 纯电 + 三厢这种结构化约束，向量召回精度远低于倒排。
- **超长尾**：车系 + 年款 + 版本的精确组合，倒排走索引效率远高于向量。

三路配额合并不是保守策略，是工程上的必要冗余。

### Q2：Quota Snake Merge 比加权求和好在哪？

加权求和（每一路给个权重，按总分排序）的问题是权重一旦定下来，在不同 query 类型下都用同一个。结构化 query 时向量路噪声被加进去，描述性 query 时倒排的精确匹配反而拉不起来。

Snake Merge 按名次轮转，每一路的 Top-1 一定在最终候选池里，Top-2 也一定在。这在"至少保证每一路的最优结果不被淹没"这个目标上更直接。线上实际做法是配额可调，但合并顺序固定。

### Q3：精排为什么要走 LLM 蒸馏而不直接用 LLM？

成本和延迟。直接用 `qwen3-30B-A3B` 做精排，P90 不可能压到 91ms，QPS 也扛不住。蒸馏到 `qwen3-1.7B` 的好处是把 LLM 的判断能力压到一个延迟可控的模型里，相关性判断精度的损失可以通过 5 档标注和 Hard Case Mining 补回来。

Level-Wise Relevance 5 档标注是这里的关键——只有 0/1 二元相关性的话，蒸馏后小模型学到的信息密度太低，必须用多档标签保留梯度。

### Q4：综合得分的 0.6/0.3/0.1 权重怎么定的？

A/B 实验反复调出来的。直觉上语义相关性应该占主导（0.6），销量反映真实市场接受度（0.3），热度作为信号补充（0.1）。

试过几个变体：

- `0.8 / 0.15 / 0.05`：相关性权重太高，长尾小众车型容易排在前面。
- `0.4 / 0.4 / 0.2`：销量权重太高，搜冷门品牌时大销量车被强行插进来。
- `0.6 / 0.3 / 0.1`：线上指标最稳，作为当前基线。

权重不是永恒的，query 类型分层之后可能针对不同 query 簇跑不同权重。

### Q5：98.07% 准确率里剩下的 2% 主要是什么？

三类为主：

- **新车别称**：2024-2025 新发布车型的别名没进训练集，`Plan-2` 识别失败。
- **年款版本**：2023 款 vs 2024 款、Pro vs Max 这类细粒度区分，训练数据密度不够。
- **海外版 / 国内版**：奔驰 GLC 海外版和国内版动力、配置、价格差异大，模型容易合并。

解法是每月增量数据更新 + 针对性 badcase 采样，没有银弹。

### Q6：车型库和 RAG 里的网页检索怎么配合？

职责分工：

- **车型库检索**：负责结构化事实——价格、配置、参数、状态。权威数据源，优先级高。
- **网页检索**：负责开放域补充——评测、对比、用户口碑、热点事件。

`Plan 模型` 在前置规划阶段决定这条 query 要不要走车型库、要不要走网页、要不要两路都走。后置融合阶段避免把车型库返回的结构化事实和网页返回的主观评测无差别混合——权威源和低可靠源无差别混合会让总结模型在口径上迷失。

## 小结

车型库检索不是"多接几个数据源"就能做好的事。关键在于四层架构的职责分离、多路召回的配额控制、精排的 LLM 蒸馏路径，以及应用层对业务指标和兜底语气的专门处理。98.07% 的车型边界识别准确率、91ms 的精排延迟、`0.6 / 0.3 / 0.1` 的综合得分权重这些数字，背后是完整的失败复盘和迭代闭环。

车型库检索做扎实以后，很多看起来属于 answer 或 plan 的问题会自然变浅——这就是为什么它值得作为整套系统最优先投入的基础设施。
