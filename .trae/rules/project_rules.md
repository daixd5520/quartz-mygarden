# quartz-mygarden 项目规则

## 项目定位

这是一个基于 Quartz 的个人数字花园（digital garden）仓库，内容主要是 Markdown 笔记，分布在 `content/note/` 下。典型子目录：

- `content/note/bd/Tech/`：工作/技术类笔记，语气成熟、工程化、有立场，是写作风格的基准参考。
- `content/note/mine/`：个人笔记，风格需要向 `bd/Tech` 对齐。

## 写作风格总则（去 AI 味）

所有笔记写作、改写、扩写任务，默认按照"成熟的机器学习从业者/研究者口吻"来写，参考基准是 `content/note/bd/Tech/` 下的已有文档（如 `Tech--RAG.md`、`Tech--RL 算法对比.md`）。

### 必须遵守

1. **克制使用视觉装饰**
   - 禁止使用 👉、✅、❌、🎯、⭐️ 等 emoji 作为段落引导符或列表标记。
   - 禁止使用 `---` 以外的分隔装饰（不要 `===`、`***`、连续的 emoji 分隔线）。
   - 标题层级克制，能用段落说清楚就不要拆小标题；`####` 及以下谨慎使用。

2. **避免 ChatGPT 模板化表达**
   - 不要写"关键差别就在：...""核心机制：...""一句话总结（压缩版）"这类自我提示式过渡。
   - 不要用"为什么？"/"原因是..."这种自问自答的引导句式串联段落。
   - 不要在结尾堆砌"总结 / TL;DR / 压缩版"三件套。如果要总结，一段话写完。

3. **陈述优先于讲课**
   - 用第一人称观点（"我认为"、"在我看来"、"实践里"）或直接陈述代替老师式引导。
   - 给出判断和立场，不要只罗列可能性。例："这在生产环境几乎不可行" > "这可能会带来成本问题"。
   - 允许口语化但保持专业，可以说"这个问题在面试里常被当送分题"、"没人会在训练循环里计较一个自由度"。

4. **内容有硬货**
   - 涉及算法/统计/ML 概念时，补充严格的数学表达、术语的英文原名（如 unbiased estimator、Bessel's correction）。
   - 有推导思路就写推导思路，不要只给结论。
   - 提 trade-off：有无偏性就提 MSE，有 RAG 就提长上下文，体现研究者视角。

5. **工程化视角收尾**
   - 结尾落到实践判断上："什么时候需要 / 什么时候可以忽略"，而不是重复前文。
   - 举具体例子（BN 直接除 n、HyDE、GRPO 去掉 Value Model 等）说明边界条件。

### 格式约定

- 笔记以 YAML frontmatter 开头，至少包含 `tags`：
  ```
  ---
  tags:
    - AIML
    - 基础理论
  ---
  ```
- 数学公式统一用 `$...$`（行内）和 `$$...$$`（独立块）。
- 英文术语首次出现用"中文（english term）"形式。
- 加粗用于关键概念；引用块（`>`）用于外部引文或口号式观点。
- 代码/变量名用反引号，但不要把文件链接文本用反引号包起来。

### 禁止清单

- 不用"🎉 恭喜！"/"让我们一起..."等鼓励性话术。
- 不用"首先、其次、然后、最后"这种小学作文骨架；语义连接词该省则省。
- 不用"👉 xxx" 强行制造重点，重点用加粗或独立一句话表达。
- 不用纯粹复述问题的引言段落（"这个问题本质上是..."一句话带过即可）。

## 文件操作规则

1. **改写任务优先编辑原文件**，不要新建副本或 `.v2.md`。
2. **不要主动创建 README 或 index 文件**，除非用户明确要求。
3. 图片资源沿用仓库已有约定（`![[xxx.png]]` Obsidian 风格 wiki-link）。
4. 修改 `content/note/bd/Tech/` 下文件前先通读上下文，它是风格基准，不要引入新的写作习惯。

## 规则迭代

这个文件是活的。用户每次提出新的写作偏好、风格约束、格式要求，都应该沉淀到本文件对应小节，而不是只在当次对话里应用。
